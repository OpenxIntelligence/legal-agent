# Agentic infrastructure: selection guide for Legal Agent

Assessment: 2026-11-04. This is a project decision guide, not an installation plan or a claim that the listed candidates are deployed. Upstream `main` license observations below are not certification of a pinned release, SDK, dependency tree, container image, or hosted service.

## Decision and current baseline

Keep the working document-and-conversation workspace and its evidence contracts. First make execution boundaries, recovery, and message delivery reliable. Add external infrastructure only when a measured requirement cannot be met by the local implementation. A useful next milestone needs no distributed service fleet.

The current application is a trusted local, loopback operator console, not an authenticated multi-tenant service. It saves matters and runs in files/JSON, launches subprocess jobs, supports queued steering and versioned review copies, and exposes bounded, matter-scoped read-only record views. The record explorer builds an in-memory SQLite projection; it is neither a persistent database connection nor an Auto Ontology integration. Demo mode uses fictional records and disables model calls. Live investigations send authorized matter content to the configured provider.

The process environment now uses an explicit allowlist for ordinary system settings, supported agent configuration, and model/CourtListener credentials. This reduces accidental inheritance of unrelated secrets. It does not prevent a process from reading files or using the network with the local account's permissions. The model credential remains available to the model worker. Settings stores local plaintext configuration with owner-only permissions, not an encrypted vault. See [execution protections](settings-and-execution.md), [README](../../README.md), and the current implementation in [ui.py](../../ui/ui.py).

## Eighteen responsibilities and adoption triggers

“Current” describes repository capability, not a production assurance. Candidates require a scoped experiment and the acceptance gates below; a protocol or SDK alone is not an operating service.

| # | Responsibility | Current capability / material gap | Selection and adoption trigger |
| --- | --- | --- | --- |
| 1 | Sandbox and secure execution | Local subprocesses; environment allowlist, but no enforced OS filesystem/network sandbox. | Evaluate **one** of OpenShell or OpenSandbox against the deny tests below. Adopt before executing untrusted tools or accepting records from other users; a trusted local pilot must disclose the remaining account-level access. |
| 2 | Agent harness and orchestration | Custom model/tool loop, evidence verifiers, budgets and orchestration contracts. Design coverage does not establish every engine is integrated into the live loop. | Retain existing contracts. | 14 | Kubernetes | No required cluster; application runs locally. | Defer. Adopt only after isolated worker fleet scheduling, availability or resource quotas justify cluster operations. A cluster does not itself supply tenant isolation, safe credentials, backups or application authorization. |
| 15 | Storage and analytics | Local files/JSON plus ephemeral SQLite record projections with six allowlisted tables and execution/output bounds. | Add persistent relational/object storage for concurrent transactions, retention and recoverable backups. | 16 | Ingestion and retrieval | Uploaded PDF/text/Markdown, preparation receipts, source viewers and evidence tools; failures/quarantine remain visible. | Improve measured extraction/search gaps first. Add one necessary connector only after checking exact component rights, incremental sync, provenance, deletion and access propagation. ## Protocol, runtime and licensing corrections

**A2A and MCP are complementary standards.** A2A addresses agent-to-agent collaboration; MCP connects applications to tools, resources and external systems. A specification is separate from a Python/TypeScript SDK, server, gateway, container and deployment. Select and audit the exact implementation rather than assigning a protocol's license to every component. Sources: [A2A](https://a2a-protocol.org/latest/) and [MCP introduction](https://modelcontextprotocol.io/docs/getting-started/intro).

**OpenShell and OpenSandbox are alternative experiments, not two mandatory layers.** OpenShell upstream documents Linux, Apple Silicon macOS and experimental WSL 2, with Docker, Podman or host virtualization prerequisites. OpenSandbox documents a local Docker path and Python 3.10+ for its quick-start tooling/examples, with a path to Kubernetes. Verify the selected release's support matrix on the actual host; neither README establishes enforcement in Legal Agent. Sources: [OpenShell README](https://github.com/NVIDIA/OpenShell/blob/main/README.md) and [OpenSandbox README](https://github.com/opensandbox-group/OpenSandbox/blob/main/README.md).

Observed upstream top-level licenses on this assessment date: [OpenShell Apache-2.0](https://github.com/NVIDIA/OpenShell/blob/main/LICENSE), [OpenSandbox Apache-2.0](https://github.com/opensandbox-group/OpenSandbox/blob/main/LICENSE), [Temporal server MIT](https://github.com/temporalio/temporal/blob/main/LICENSE), and [OpenTelemetry Python Apache-2.0](https://github.com/open-telemetry/opentelemetry-python/blob/main/LICENSE). These observations do not certify SDKs, plugins, images, OS packages, model weights, drivers, cloud terms or a complete deployment. Pin commits/releases and image digests, inventory transitive artifacts, retain notices, and review distribution and service obligations before adoption.

**Airbyte requires exact component review.** Current upstream licensing documentation identifies Airbyte Protocol as MIT, describes connectors/other public repository components under ELv2, and distinguishes commercially licensed offerings. Inspect the chosen connector's metadata and license at a pinned version; do not carry forward a generic “Airbyte is MIT” label or assume every historically described component has the same current terms. Source: [Airbyte licensing documentation](https://github.com/airbytehq/airbyte/blob/master/docs/community/licenses/README.md).

**OpenTelemetry is instrumentation and signal transport, not the storage backend.** An SDK and collector do not choose retention, residency, access or a dashboard automatically. Temporal supplies durable workflow infrastructure; it does not validate evidence or make external provider operations intrinsically exactly-once. Sources: [OpenTelemetry overview](https://opentelemetry.io/docs/what-is-opentelemetry/) and [Temporal documentation](https://docs.temporal.io/temporal).

The existing project also needs its own dependency audit. [requirements.txt](../../agent/requirements.txt) declares OpenAI client, eyecite, reporters-db, pdfplumber, reportlab and pypdfium2; ranges are not a resolved inventory. The optional `pdftoppm` executable invoked by [reset_case.py](../../agent/scripts/reset_case.py) comes from Poppler and sits outside that Python list. Check its actual installed version, packaging and license before including it in a distribution. No claim that the present runtime satisfies a strict permissive-only policy is made here.

## Deployment ladder and priorities

1. **Local synthetic demonstration — current baseline.** Keep fictional inputs, no provider access and clear labels. Validate intake, uploads, chat, source access, review versions and export through the existing harness. This demonstrates interaction and provenance mechanics, not legal accuracy.
2. **Trusted single-operator live pilot — next engineering target.** Prioritize the common execution boundary, durable job ownership/receipts and crash-safe steering. Use permissioned non-sensitive or synthetic tasks first. Live tests require an explicit provider/spend authorization; environment tests use fake credentials. Retain loopback binding and honest unsandboxed status until deny tests pass.
3. **Single hosted pilot with isolated workers — conditional.** Add HTTPS authentication, server-side matter membership, transactional state, per-job sandbox policy, scoped credentials and backup/restore. A small service plus isolated workers may suffice; Kubernetes, event brokers and model gateways remain conditional.
4. **Multi-tenant/distributed operation — separate readiness decision.** Require demonstrated tenant separation, lifecycle deletion, resource quotas, durable workflows, incident operations and reviewer calibration. Adopt Temporal, a broker, Kubernetes or connectors only against their corresponding row's trigger and operational ownership.

The local reliability baseline now includes runner ownership locks, explicit abandoned-checkpoint recovery, and atomic steering payload/ID checkpoints. These are tested with process termination and write/ack fault injection; they do not guarantee exactly-once tool effects. Before adding distributed infrastructure, complete the remaining durability gaps. First, console logs and launch discovery remain in memory: persist launch intent and completion receipts in addition to the ownership lock and explicit recovery action. A saved status of “running” is not a resumable live process. Second, preserve the steering checkpoint-before-receipt contract as execution becomes distributed; the current fix prevents the identified local loss window but is not a multi-writer transaction. Validate those failure windows with process termination tests rather than UI success text.

## Acceptance gates for any adoption

Record a short decision with the requirement, smallest alternative, owner, pinned versions, license inventory, rollback, measured result and unresolved limits. A candidate progresses only when these gates pass:

- **Execution:** immutable authorized input; separate writable output; denied sibling matters, fake secrets, host writes, arbitrary egress and runtime sockets. Exercise child processes, cancellation, timeouts and missing-policy/runtime failures. Fail closed and record the actual runtime/policy in each run receipt. Environment filtering alone does not pass this gate.
- **Recovery and cost:** crash at launch, message delivery, provider activity and completion boundaries. Reconcile ownership, deduplicate directives, retain evidence versions, and never silently replay an ambiguous paid operation. Define retries and cancellation for every external side effect.
- **Resources:** measure cold start, resident memory, CPU, disk/image growth, file descriptors, maximum concurrent jobs and provider spend on representative documents. Set per-job and per-operator quotas, timeouts and cleanup. Include GPU/virtualization requirements if introduced; benchmark the target host rather than quoting vendor throughput.
- **Tenancy:** attempt forged matter/run/source IDs, cross-tenant queries, stale source handles and revoked access after a cached result. Verify worker mounts, database authorization, logs and exports all obey the same scope. A shared deployment needs an explicit threat model for co-resident workloads.
- **Residency and PII:** inventory document text, metadata, prompts, embeddings, caches, traces, backups and support uploads. Specify region, provider retention/training terms, access roles, deletion/restore behavior and privilege handling. Test that sensitive content stays out of telemetry and error messages. Obtain required organizational review before real client records.
- **Quality and operations:** retain a permissioned reviewer-labeled evaluation set and separate retrieval, quote integrity, semantic support and legal correctness. Test outages, rollback, backup restore and credential rotation. Name the operator and incident process before accepting availability promises.

Passing an infrastructure gate does not approve a legal conclusion. Preserve the workspace's evidence links, explicit uncertainty and human review throughout every deployment stage.
